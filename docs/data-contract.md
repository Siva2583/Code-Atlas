## Stable identities and logical types

The CSV contract uses UTF-8 text, comma delimiters, RFC 4180 quoting, and an exact ordered header. A leading UTF-8 BOM is allowed and stripped. Dates use YYYY-MM-DD and must be real calendar dates. Integer fields are base-10, non-negative, with no decimal or grouping characters.

| Concept | Candidate rule |
|---|---|
| Source system | Identifier provisioned in the SAP tenant before object imports. There is no source-system CSV. An unknown identifier is rejected. |
| Custom object business key | Trimmed, case-normalized source_system + object_type + object_name. The technical ObjectUUID is generated by the persistence layer and is not supplied in CSV. |
| Usage fact key | Custom object business key + period_start + period_end + evidence_source. |
| Finding key | Custom object business key + finding_id + check_id + source_reference. |
| Dependency key | Source system + from_type + from_name + to_type + to_name + dependency_type + evidence_source. |
| UUIDs | Opaque technical UUIDs generated by the SAP layer. Concrete ABAP UUID types are not selected until the tenant's released APIs are verified. |
| Text limits | Physical field lengths and request/file size limits are not confirmed in the empty SAP object placeholders. They remain a Day 1 capability/schema decision; do not silently truncate input. |

All key fields are trimmed; source_system, object_type, object_name, enum values and dependency_type are normalized to uppercase for matching. Free-text descriptions, messages and source references retain their content. Empty optional dates remain unknown, not zero dates.

## Exact candidate CSV schemas

The headers below are in required order. The objects header adds findings_as_of at the end; this is a proposed schema change and requires shared sign-off before implementation.

| File | Ordered header |
|---|---|
| objects.csv | source_system, object_type, object_name, package, description, criticality, business_owner, first_seen, last_seen, findings_as_of |
| usage.csv | source_system, object_type, object_name, period_start, period_end, last_executed, run_count, evidence_source, evidence_as_of |
| findings.csv | source_system, object_type, object_name, finding_id, check_id, category, severity, message, source_reference |
| dependencies.csv | source_system, from_type, from_name, to_type, to_name, dependency_type, evidence_source |

### Field rules

- objects: source_system, object_type and object_name are required identifiers. package, description and business_owner are text. criticality accepts HIGH, MEDIUM, LOW or UNKNOWN; an empty value normalizes to UNKNOWN. first_seen, last_seen and findings_as_of are optional dates. A populated findings_as_of means the finding scan is complete for that object as of that date, even when findings.csv contains no rows for it. Blank means findings coverage is unknown; consumers must not infer zero findings.
- usage: object identity, period_start, period_end, run_count, evidence_source and evidence_as_of are required. last_executed may be blank. run_count is a non-negative integer. evidence_source accepts DEMO or CSV_EXPORT for this MVP; LIVE_ADAPTER is reserved until a live adapter is verified. A valid but contradictory observation is retained for the rule layer to classify as conflicting evidence.
- findings: object identity, finding_id, check_id and severity are required. severity accepts HIGH, MEDIUM, LOW or INFO; blank severity is rejected. category, message and source_reference are text and may be blank.
- dependencies: both endpoint identities, source_system, dependency_type and evidence_source are required. evidence_source accepts DEMO or CSV_EXPORT for this MVP. Both endpoints must already exist. dependency_type is an uppercase non-empty token; no closed list is approved yet.

The rules specification still owns the rule oracle. This candidate resolves only the findings-loaded-versus-no-findings ambiguity with findings_as_of. REWRITE_RAP and SIDE_BY_SIDE_BTP remain untestable until Member 2 approves additional source fields; Member 1 does not invent those fields here.

## Batch, row and provenance contract

One uploaded file is one ImportBatch with one file kind. BatchUUID is generated by the server for every attempt, including repeat uploads. The batch stores file kind, SHA-256 of the original file bytes, actor, UTC creation time, parsed/accepted/rejected counts and status.

Accepted row results are INSERTED, UPDATED or UNCHANGED. Rejected rows have result REJECTED plus a stable error code. Accepted count = INSERTED + UPDATED + UNCHANGED; rejected count = REJECTED; parsed data-row count = accepted + rejected. The header is not a data row.

A source row is the one-based CSV record number including the header: the header is row 1 and the first data record is row 2. Record number, not physical text line, is used because quoted fields may contain newlines.

Repeated business keys within one file are all rejected as DUPLICATE_KEY; neither duplicate occurrence is applied. A repeat in a later batch with an identical normalized payload returns UNCHANGED. A later batch with the same key and corrected non-key values returns UPDATED. A corrected batch never deletes omitted entities or prior batch/provenance records.

Row-level validation rejects do not discard unrelated valid rows. Valid rows from one file may commit together while rejected rows and their errors are persisted; the batch status is COMMITTED if at least one row is accepted, including an all-UNCHANGED batch. A header-only file fails with EMPTY_FILE. A fatal persistence error rolls back that file's business-row writes and marks the batch FAILED. No row may be silently dropped.

Every rejected row must retain BatchUUID, file kind, source record number, business key when parseable, field, error code and message. Every accepted row must retain equivalent batch/file/record/key/result provenance. An append-only row-result ledger is the proposed way to satisfy this; whether it can be activated is a Day 1 tenant check. If unsupported, accepted-row historical provenance is blocked and must not be claimed.

## Stable error codes

| Code | Meaning |
|---|---|
| HEADER_MISMATCH | Header name, order, missing column or extra column differs from the candidate schema. |
| MALFORMED_CSV | Invalid quoting or an unreadable CSV record. |
| COLUMN_COUNT_MISMATCH | Data record does not contain the exact number of fields. |
| MISSING_REQUIRED_FIELD | Required identifier or value is blank. |
| INVALID_ENUM | Value is outside the approved MVP enumeration. |
| INVALID_DATE | Date is malformed or not a calendar date. |
| INVALID_INTEGER | Integer syntax is invalid. |
| NEGATIVE_RUN_COUNT | run_count is below zero. |
| DUPLICATE_KEY | Business key appears more than once in one input file. |
| UNKNOWN_SOURCE_SYSTEM | Object references a source system not provisioned in the tenant. |
| UNKNOWN_OBJECT | Usage/finding/dependency row references an object not already persisted. |
| EMPTY_FILE | Header is present but there are no data records. |
| PERSISTENCE_FAILURE | Fatal storage failure; the file's business-row transaction is rolled back. |
